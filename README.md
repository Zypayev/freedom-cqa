# CQA — Conversation Quality Analytics
Ramazan Zypayev, Beibars Ybraykhan, Zhalgas

Прототип для хакатона Freedom Broker: автоматическая оценка работы оператора по настраиваемому чек-листу, ссылки на реплики-доказательства, апелляции с пересчётом итога, версии чек-листов и замер точности относительно эталона.

## Быстрый старт

Нужен Python 3.11+.

```bash
cp .env.example .env          # укажите CQA_DATASET_URL; модель — см. «Модель и стоимость» (по умолчанию локальная Ollama)
cd backend
python -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/uvicorn app.main:app --port 8000
```

Windows (PowerShell):

```powershell
Copy-Item .env.example .env
cd backend; python -m venv .venv; .\.venv\Scripts\pip install -r requirements.txt
.\.venv\Scripts\python.exe -m uvicorn app.main:app --port 8000
```

Откройте http://localhost:8000. При первом запуске создаётся база `data/cqa.sqlite3` и загружается чек-лист из PDF ([chat_quality_v1.json](backend/app/checklists/chat_quality_v1.json)).

Для работы без сети есть синтетические примеры диалогов: на странице «Диалоги» выберите «Файл JSON» → [data/sample_dataset.json](data/sample_dataset.json). Это примеры команды, а не данные организаторов.

Тесты (сеть и ключ не нужны):

```bash
cd backend && .venv/bin/python -m pytest -q
```

## Как пользоваться

1. **Диалоги → Загрузка данных.** Введите `group_id` (например `DEV`) и нажмите «Загрузить из API». Запрос идёт через backend, поэтому CORS не мешает. Исходные метки времени сохраняются как есть.
2. **Оценка набора.** Выберите чек-лист и число прогонов и нажмите «Оценить набор». Прогресс и стоимость видны сразу.
3. **Карточка диалога.** Транскрипт слева, результат справа: ответ, баллы, перераспределённый вес, объяснение, доказательства, причина N/A, проверенный участок. Клик по `tXX` прокручивает к реплике и подсвечивает её. У звонков клик ещё и перематывает запись.
4. **Апелляция.** В роли «Оператор / супервайзер» нажмите «Оспорить оценку» у критерия. Переключите роль на «Проверяющий» и откройте «Апелляции». Там видны спорная оценка, комментарий и фрагмент диалога с доказательствами. Подтвердите или измените оценку с причиной, итог пересчитается. В карточке остаются исходная оценка, решение и финальный итог.
5. **Чек-листы.** Добавляйте, удаляйте и меняйте критерии, вес, тип (Да/Нет, шкала, флаг), N/A с условием, ступени шкалы, формулировки для чата и звонка, секции и базу знаний. «Сохранить как новую версию», затем «Переоценить набор». Старые оценки остаются в истории с привязкой к своей версии.
6. **Точность.** В карточке включите «Режим эталонной разметки» и проставьте эталонные ответы. Страница «Точность» покажет совпадение по каждому критерию, ошибки N/A и среднюю ошибку итога.

### Сдача результатов (формат JSON 1.0 организаторов)

```bash
cd backend
.venv/bin/python -m app.export_results --dataset DEV --out ../results/dev/results.json
.venv/bin/python -m app.export_results --dataset <group_id контрольного набора> --out ../results/prod/results.json
```

Коды критериев (`contact`, `discovery`, …, `critical`) берутся из поля `export_id` чек-листа, номера реплик — порядковые номера в исходном транскрипте (с 1). Берётся исходная оценка системы по активной версии чек-листа; неоценённые диалоги попадают со `status: "error"`. Название команды — `--team` или `CQA_TEAM_NAME` в `.env`.

Порядок на контроле: «Загрузить из API» с новым `group_id` → «Оценить набор» → выгрузка в `results/prod/results.json` → `git commit` и `git push`.

### Сценарий защиты (5 минут)

| Минуты | Что показать | Где |
|---|---|---|
| 1 | Список, фильтры, карточка | Диалоги → карточка |
| 2 | Обоснование, клик по `tXX`, пример N/A с перераспределением веса, итог и секции | Карточка |

## Как устроена оценка

```
транскрипт ─► факты (код) ─► промпт из чек-листа ─► LLM ×N ─► проверка ─► голосование ─► баллы (код)
```

- **Модель только отвечает по критериям, баллы считает код** ([scoring.py](backend/app/scoring.py)). «Да» даёт полный вес, «Нет» — 0, шкала считается как ступень / верхняя ступень × вес. N/A исключается, и его вес пропорционально перераспределяется до 100. Итог округляется до 2 знаков (половина вверх). Грубые ошибки отмечаются отдельно. Поэтому итог воспроизводим, а после апелляции пересчитывается мгновенно.
- **Часть фактов считает код** ([facts.py](backend/app/facts.py)): ID реплик, время первой реакции относительно порога 3 минуты, долгие ожидания и было ли предупреждение, язык клиента и язык первого ответа оператора, системные события, темп речи на звонках. Модель получает их как точные данные.
- **Промпт и JSON-схема собираются только из чек-листа** ([prompt.py](backend/app/prompt.py)). Ни одного критерия в коде нет, поэтому новый или заменённый критерий работает сразу после сохранения. Схема ограничивает ответы допустимыми значениями (`yes/no/na` или ступени шкалы), а ссылки — существующими ID реплик.
- **Сначала разбор, потом ответ.** В схеме поле `analysis` стоит перед `answer`.
- **Проверка ответа** ([evaluator.py](backend/app/evaluator.py)). Проверяется, что у N/A есть причина, что есть доказательство или место, где действие ожидалось, и что «Да» не подтверждено только репликами клиента или бота. При нарушении модель получает замечания и отвечает повторно.
- **Голосование.** При N прогонах ответ выбирается большинством по каждому критерию. Расхождение снижает уверенность, и критерий попадает в «нужна ручная проверка».
- **Звонки.** Для критерия 6 используется отдельная формулировка: логичность, понятность, формулировки и паузы. Дикция по транскрипту не оценивается.
- **Журнал.** Каждый вызов модели сохраняется: модель, токены (в том числе из кэша), длительность, стоимость, сырой ответ и замечания проверки. Видно, что диалог действительно оценивается, а не подставляется готовый результат.

### Модель и стоимость

**Используемая модель: локальная `qwen3:14b` через [Ollama](https://ollama.com), бесплатно ($0 за оценку).** Работает на RTX 4070 Super 12 ГБ целиком в видеопамяти: около 40 с на диалог при двух параллельных оценках, все 65 диалогов DEV — около 46 минут. Данные не покидают контур. Измерено: ~3,8–6,8 тыс. входных и ~1,3–1,5 тыс. выходных токенов на диалог.

Настройка (`.env`):

```
CQA_PROVIDER=ollama
CQA_OLLAMA_MODEL=qwen3:14b
OLLAMA_URL=http://localhost:11434
CQA_OLLAMA_NUM_CTX=16384
CQA_CONCURRENCY=2
```

```bash
ollama pull qwen3:14b
# чтобы 14B с контекстом 16k поместилась в 12 ГБ:
OLLAMA_FLASH_ATTENTION=1 OLLAMA_KV_CACHE_TYPE=q8_0 ollama serve
```

Нужна видеокарта NVIDIA с ~12 ГБ памяти; на процессоре работает, но очень медленно. Без видеокарты можно взять `qwen3:8b`.

**Облачная альтернатива:** `CQA_PROVIDER=anthropic`, `ANTHROPIC_API_KEY=...`, `CQA_MODEL=claude-opus-5-5` ($4 / $20 за 1M входных / выходных токенов, `effort=high`). Системный промпт с чек-листом кэшируется. Ориентир: $0.08–0.15 за оценку при одном прогоне, при голосовании из N прогонов — ×N. Стоимость каждой оценки считается по фактическим токенам и показывается в карточке, в списке и в ходе пакетной оценки.

## Структура

```
backend/app/
  main.py          HTTP API, фоновые задачи оценки, раздача фронтенда
  evaluator.py     прогоны LLM, проверка, повтор, голосование
  prompt.py        промпт и JSON-схема из чек-листа
  facts.py         факты, посчитанные кодом
  scoring.py       расчёт баллов по правилам чек-листа
  llm.py           адаптеры Anthropic / Ollama, учёт стоимости
  services.py      валидация чек-листа, итог с апелляциями, точность
  db.py            SQLite
  checklists/      начальный чек-лист
frontend/          HTML + CSS + JS-модули без сборки
data/              база и примеры
```

Данные: `Checklist` (версии, у каждой оценки свой снимок) → `Evaluation` (исходный результат неизменен) → `Appeal` (решение проверяющего). Финальный итог пересчитывается из исходных ответов и решений по апелляциям.

### API (основное)

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/datasets/fetch` | загрузить набор по `group_id` из API организаторов |
| POST | `/api/datasets/upload` | загрузить JSON в формате организаторов |
| GET | `/api/dialogs` | список с последней оценкой |
| POST | `/api/jobs` | оценить `dialog_ids` или `dataset` выбранной версией чек-листа |
| GET | `/api/evaluations/{id}` | результат, исходная оценка, апелляции, финальный итог |
| POST | `/api/checklists` | сохранить новую версию чек-листа |
| POST | `/api/evaluations/{id}/appeals` | подать апелляцию |
| POST | `/api/appeals/{id}/decision` | решение проверяющего (`confirm` / `change`) |
| GET | `/api/export` | CSV последних оценок |
| GET | `/api/accuracy` | точность относительно эталона |

## Dynamics 365

Фронтенд собран без сборщика и фреймворков. Он монтируется в один элемент `#cqa-root`, а все стили ограничены классом `.cqa`. Чтобы встроить его как HTML web resource:

1. Загрузите `index.html`, `css/app.css` и `js/**` как web resources, сохранив относительные пути.
2. Перед подключением `js/app.js` задайте адрес сервиса: `<script>window.CQA_API_BASE = "https://cqa.example.kz";</script>`.
3. CORS на backend уже разрешён.
